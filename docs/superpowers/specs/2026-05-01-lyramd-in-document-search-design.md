# 2026-05-01 — LyraMD 文档内搜索设计

## 摘要

本轮设计只聚焦一个明确目标：为 LyraMD 提供**当前文档内搜索**能力，并且保持产品一贯的极简气质。

范围已经明确收敛：

1. 只做当前文档内查找
2. 只做 `Find`，不做替换
3. 使用悬浮小面板，不推挤正文布局
4. `Cmd/Ctrl+F` 打开时，默认使用当前选中文本作为搜索词

这不是一次“把搜索做全”的扩面，而是给 Agent Native Markdown 编辑器补上一块应该像空气一样存在、但必须稳定可信的基础能力。

---

## 1. 设计目标

### 1.1 保持极简，不做重型搜索系统

LyraMD 当前不是 IDE，也不是知识库管理器。第一版搜索不追求跨文件、全局索引、命令面板或结果页，而是优先把“当前文档里快速找到内容”做到顺手、稳定、可预测。

### 1.2 搜索不应破坏正文编辑体验

搜索面板应该是悬浮的、短驻留的、低存在感的：

- 不增加常驻侧边栏
- 不占用正文上方固定高度
- 不因为搜索打开而重排编辑器内容

### 1.3 为后续扩展保留结构

虽然第一版只做查找，但底层结构应该能平滑扩展到：

- 大小写匹配
- 整词匹配
- 正则匹配
- 替换

因此这轮不建议继续堆叠当前仓库里纯字符串匹配的业务层实现，而是把搜索状态下沉到 ProseMirror 侧。

---

## 2. 方案对比与结论

### 2.1 方案 A：增强现有轻量搜索实现

做法：

- 保留当前 `src/renderer/editor/search.ts` 的字符串匹配逻辑
- 只在 renderer 层重做悬浮 UI 和快捷键

优点：

- 改动最小
- 上线最快

缺点：

- 高亮与跳转能力继续散落在业务层
- 后续扩展高级选项和替换时容易继续长歪
- 与 `Milkdown + ProseMirror` 的编辑器能力边界不清

### 2.2 方案 B：ProseMirror 原生化搜索

做法：

- 使用 `prosemirror-search` 承接底层搜索状态、命中高亮、当前命中项与上下跳转
- LyraMD 自己实现悬浮小面板 UI

优点：

- 最贴合当前技术栈
- 搜索逻辑与 UI 分层清晰
- 后续扩展大小写/整词/替换成本最低

缺点：

- 接入成本高于方案 A
- 需要把当前搜索状态从 renderer 业务层迁到编辑器层

### 2.3 方案 C：借用完整搜索组件思路

做法：

- 更完整地模仿 `VS Code` 或 `CodeMirror` 搜索控件
- 甚至尝试直接复用部分现成组件思路

优点：

- 交互模式成熟

缺点：

- 很容易把产品做重
- 大部分实现不能直接塞进 `Milkdown`
- 性价比最低

### 2.4 结论

本轮推荐采用 **方案 B：ProseMirror 原生化搜索**。

原因：

1. 它最符合 LyraMD 当前的技术栈边界
2. 它能保证第一版足够轻，同时避免未来搜索逻辑继续在业务层失控增长
3. 它既能吸收 `VS Code / CodeMirror` 的交互优点，又不需要把它们的整套复杂系统搬进来

## 3. 交互设计

### 3.1 入口

- `Cmd+F`（macOS）或 `Ctrl+F`（Windows / Linux）打开搜索面板
- 搜索面板以悬浮形式显示在**编辑器内容区内右上角**
- 面板出现时不改变正文布局，不推挤内容区域

### 3.2 默认搜索词

打开搜索时：

- 如果正文中当前存在选中文本，则自动将选中文本填入搜索框
- 若选区为空，则打开空搜索框
- 搜索框打开后立即获得焦点

这样既符合用户直觉，也贴近 `VS Code` 这类成熟编辑器的行为。

### 3.3 面板元素

第一版面板只包含以下元素：

- 搜索输入框
- `上一项`
- `下一项`
- `N / M` 命中计数
- `关闭`

本轮不加入：

- 替换输入框
- 大小写开关
- 正则开关
- 整词开关
- 结果列表

### 3.4 输入与跳转

- 输入时实时更新命中结果与高亮
- `Enter` 跳到下一项
- `Shift+Enter` 跳到上一项
- 当前命中项需要有比普通匹配更明显的高亮样式
- 当跳到最后一个命中后再次按 `Enter`，回环到第一个命中
- 当跳到第一个命中后再次按 `Shift+Enter`，回环到最后一个命中
- 当 query 为空时，`N / M` 显示 `0 / 0`，`Enter` 与 `Shift+Enter` 都是 no-op
- 搜索框处于中文 IME 组合输入期间时，不应把 `Enter` 或 `Esc` 误判为搜索快捷键；query 更新需要是 composition-safe 的

### 3.5 关闭与恢复

- `Esc` 关闭搜索面板
- 关闭后，焦点回到编辑器
- 用户原本的编辑位置尽量保留，避免搜索结束后打断写作流

### 3.6 再次打开

- 如果当前文档内已经存在一次搜索状态，再次按 `Cmd/Ctrl+F` 时默认保留上一次搜索词
- 但如果用户这次重新选中了新的文本，则优先用新的选中文本覆盖旧搜索词
- 搜索词按文档临时记忆：切换到其他文档时面板关闭，但当用户回到原文档并再次打开搜索时，恢复该文档上一次 query

### 3.7 无结果状态

- 无命中时显示 `0 / 0`
- 不弹额外提示
- 不阻止继续输入

## 4. 技术结构设计

### 4.1 两层结构

搜索实现分成两层：

#### 编辑器内核层

由 `prosemirror-search` 负责：

- 搜索 query 状态
- 匹配范围计算
- 匹配 decoration / 高亮
- 当前 active match
- 上一项 / 下一项跳转

#### LyraMD UI 层

由 renderer 负责：

- 悬浮搜索面板 DOM
- 快捷键触发
- 搜索输入同步
- `N / M` 展示
- 打开、关闭、焦点恢复

### 4.2 为什么不继续把搜索状态留在 main.ts

当前实现中，搜索状态更多是以“当前 Markdown 字符串 + 业务层状态”方式存在。这对于最小原型是够用的，但对正式编辑器能力来说边界不够清晰。

如果继续沿着这个方向长：

- 高亮定位会越来越依赖手工位置映射
- 选区、跳转、热更新三者容易互相打架
- 未来要加入更复杂搜索选项会让 renderer 逻辑越来越重

将搜索状态迁到 ProseMirror 内核层后，编辑器本身会成为搜索的唯一真相源，renderer 只消费状态并驱动 UI。

### 4.3 现有搜索代码的处理建议

现有的 `src/renderer/editor/search.ts` 不一定要整份保留为正式实现，但其中一些轻量接口命名和 preview 相关能力可以评估是否保留为：

- UI 层适配器
- 测试夹具
- 后续“搜索结果预览”演进的基础

本轮不建议继续扩大它作为主搜索引擎的职责。

## 5. 边界行为

### 5.1 焦点规则

- 打开搜索后，焦点在搜索输入框
- 关闭搜索后，焦点回到编辑器
- 焦点恢复时尽量保留用户原本的编辑位置
- 搜索相关快捷键只在搜索输入框聚焦时接管 `Enter`、`Shift+Enter` 与 `Esc`
- 如果面板仍开着，但焦点已回到编辑器正文，则正文输入语义优先，`Enter` 继续作为换行而不是搜索跳转

### 5.2 选区规则

- 当前选区只用于“搜索打开时的预填充”
- 搜索跳转过程中，不应把正文永久留在异常选区状态
- 搜索不应破坏正常编辑时的光标语义

### 5.3 外部热更新

LyraMD 的核心卖点之一是外部 Agent 修改文件时，正文可实时刷新。因此搜索必须和热更新和平共处：

- 如果文档内容被外部更新，搜索结果应重新计算
- 如果搜索面板仍然打开，则继续保持打开
- 若搜索词未变，面板上的 `N / M` 应同步更新
- 若原 active match 已失效，命中项回退规则明确为：
  - 优先取更新后位置不晚于原 active match 的最近后继命中
  - 若不存在后继命中，则取最近前驱命中
  - 若已经没有任何命中，则 active 清空，但面板保留打开

### 5.4 切换文档

- 切换到另一个文档时，搜索面板默认关闭
- 不将一个文档的搜索面板直接带到另一个文档
- 但每个文档可以各自保留一次临时搜索词，用于再次打开时恢复

### 5.5 空文档与短文档

- 空文档允许正常打开搜索
- 无内容时稳定显示 `0 / 0`

### 5.6 长文档性能

第一版至少需要保证常见 Markdown 文稿下输入搜索词时体感顺畅。

如果在真实使用中发现“每输入一个字都明显卡顿”，再评估：

- 是否需要输入防抖
- 是否需要限制超大文档时的即时刷新策略

本轮不预先引入复杂性能优化，优先保持实现简洁。

---

## 6. 非目标

本轮明确不做：

1. 跨文档 / 工作目录搜索
2. 替换
3. 搜索结果列表
4. 命令面板式搜索
5. 搜索历史
6. 大小写 / 整词 / 正则高级选项

这些都可以作为后续 phase，但不属于本轮范围。

---

## 7. 验收标准

第一版完成后，至少满足以下人工验收条件：

1. `Cmd/Ctrl+F` 可以稳定打开悬浮搜索框
2. 搜索框打开时不会推挤正文布局
3. 有选中文本时会自动填入搜索词
4. 输入时实时高亮匹配结果
5. `Enter` / `Shift+Enter` 可在匹配项之间跳转
6. 面板正确显示 `N / M`，无结果时显示 `0 / 0`
7. `Esc` 关闭后可以立即回到正文继续编辑
8. 中文输入法组合输入期间，搜索不会错误响应 `Enter` / `Esc`
9. 外部 Agent 修改当前文件后，搜索结果会重新计算且不丢状态
10. 切换到其他文档后，旧文档面板不会残留；切回原文档后可恢复该文档上次搜索词

---

## 8. 推荐实施顺序

### Phase 1：内核接入

- 评估并接入 `prosemirror-search`
- 建立 editor 层搜索状态与跳转命令

### Phase 2：悬浮 UI

- 接入 `Cmd/Ctrl+F`
- 实现悬浮搜索面板
- 打通输入、高亮、计数、上下跳转、关闭

### Phase 3：边界打磨

- 验证焦点恢复
- 验证外部热更新后的搜索状态一致性
- 验证长文档与空文档表现

---

## 9. 参考方向

本轮设计主要吸收的是“交互模式”和“分层思路”，不是照搬完整搜索系统：

- `VS Code`
  借鉴轻量 find widget 的交互协议：`Cmd/Ctrl+F`、selection seed、`Enter/Shift+Enter`、`N / M`
- `CodeMirror`
  借鉴搜索面板与编辑器搜索状态分层的思路
- `ProseMirror / prosemirror-search`
  作为当前技术栈最合适的底层搜索能力承载点

LyraMD 的第一版目标不是成为 IDE，而是把 Markdown 文档内搜索做得足够轻、稳、顺手。
