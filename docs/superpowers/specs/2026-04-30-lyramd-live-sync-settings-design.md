# 2026-04-30 — LyraMD 实时同步与文档交互设计

## 摘要

本轮设计聚焦 5 个已经暴露为真实使用阻塞的问题：

1. 外部 Agent 修改当前文件后，LyraMD 不能稳定实时刷新
2. 文档开头标题变化后，窗口标题与文件名缺少同步策略
3. 缺少一个轻量、悬浮式的设置入口来承载这些行为偏好
4. “另存为”缺少更清晰的路径迁移语义，包括“另存为后删除当前路径”
5. 复制多段内容时出现额外空行与 `br` 泄漏

本轮不追求扩面，只修 LyraMD 的核心承诺：让 Agent 改文档时，人类看到的是可靠、可控、可理解的结果。

---

## 1. 设计目标

### 1.1 恢复产品第一原则

LyraMD 的基础承诺不是“能编辑 Markdown”，而是“人类和 Agent 可以围绕同一个 Markdown 文件顺滑协作”。因此外部修改实时可见不是增强项，而是底座。

### 1.2 控制新增实体

- 不新增工具栏
- 不引入复杂设置页或多级导航
- 设置只做成一个悬浮面板
- 只有在用户真的遇到命名决策时，才出现命名提示

### 1.3 显式区分“同步内容”和“同步身份”

需要把两类问题分开：

- **内容同步**：文件内容变了，编辑器应该刷新
- **身份同步**：标题、文件名、保存路径这些“文档身份”要不要跟着变

内容同步默认自动；身份同步必须可解释、可拒绝、可配置。

## 2. 实时热更新设计

### 2.1 问题判断

当前实现只监听单文件 `fs.watch(filePath)` 的 `change` 事件。这个模型假设外部工具会“原地写文件”，但现实里很多 Agent / 编辑器会采用“写临时文件后 rename 覆盖”的原子替换模式。

在 macOS 上，这种写法常见结果是：

- 只收到 `rename`
- 原 watcher 在 rename 后失效
- 后续再写文件也不再上报

这意味着“只处理 `change`”的模型先天不够。

### 2.2 目标行为

当当前文件被外部进程修改时：

1. LyraMD 应在短时间内检测到变化
2. 如果当前没有待落盘的本地修改，直接刷新内容
3. 如果当前正有本地保存队列，先 defer，再在本地队列空闲后应用外部变化
4. 如果文件是通过 rename 被替换，监听应自动恢复，不要求重开应用

### 2.3 推荐实现方向

主策略建议分两层：

1. 保留“当前打开文件”的精确监听语义
2. 监听实现上补足 `rename` 场景

推荐顺序：

- 第一阶段：继续以当前文件为中心，但显式处理 `rename`
- 第二阶段：收到 `rename` 后自动重绑 watcher，并主动重新读取文件
- 如果实践证明单文件 watcher 仍不稳，再升级到“监听父目录 + 匹配目标文件路径”的模型

### 2.4 非目标

本轮不做：

- 多文件协同刷新
- 文件删除/冲突解决 UI
- 类 Git diff 视图

## 3. 标题、文件名与身份同步设计

### 3.1 问题判断

当前正式文件窗口标题只取 basename，正文首个 `#` 标题改变后不会联动。草稿有 `displayTitle` 机制，正式文件没有对应策略，因此用户会看到：

- 文档标题已经变了
- 窗口标题没变
- 文件名更不会变

### 3.2 目标行为

系统需要同时支持三件事：

1. **窗口标题实时反映当前文档标题**
2. **用户可决定是否把文档标题同步成文件名**
3. **这种决定可以被记住，后续进入设置修改**

### 3.3 具体策略

#### 窗口标题

- 对正式文件，不再只显示 basename
- 优先显示“当前文档标题”，没有标题时回退到 basename
- 这样可以立即解决“标题变了但窗口无感知”的问题

#### 文件名同步提醒

当满足以下条件时，触发一次轻量提醒：

- 当前文档已有真实路径
- 文档首个一级标题发生变化
- 新标题与当前文件名存在明显差异
- 这次变化不是程序性刷新，而是用户主动编辑造成

提醒提供 3 个选项：

1. `仅同步这次`
2. `以后都自动询问`
3. `不要再提醒`

如果用户选择同步：

- 打开一个受控的重命名流程
- 修改文件路径
- 保持当前文档会话继续指向新路径
- 更新 recent/workdir/sidebar 中的相关引用

### 3.4 双击改标题

在当前文档标题区域支持双击进入轻量编辑态：

- 默认编辑“文档标题显示值”
- 若用户确认并启用同步文件名，则连带进入文件重命名

这提供一个显式、可发现的入口，避免所有命名行为都依赖正文开头的 Markdown 标题。

### 3.5 风险边界

不应默认无提示直接改文件名，因为：

- 有些用户故意让文件名和标题不同
- 直接 rename 可能影响外部脚本、recent 列表和工作目录定位
- 这是“身份变化”，不该和普通内容同步一样静默发生

## 4. 设置面板设计

### 4.1 形态

设置采用悬浮 modal，覆盖在编辑器上方，不分标签页，不做左侧导航。

原则：

- 轻量
- 一屏看完
- 能承载少量偏好开关

### 4.2 首批设置项

首版只收纳与本轮问题直接相关的项目：

1. 标题变化时的文件名同步策略
2. 默认草稿目录
3. “另存为”的默认后续行为
4. 主题/导入主题
5. Agent 活动指示点开关

### 4.3 标题同步策略枚举

建议支持以下枚举值：

- `ask`
- `always`
- `never`

默认值建议为 `ask`。

### 4.4 另存为默认行为枚举

用户这轮明确提出需要支持一个额外选项：`另存为后删除当前路径`。

因此建议设置中显式支持：

- `switch`
  说明：另存为成功后，当前会话切换到新路径，旧路径保留
- `move`
  说明：另存为成功后，当前会话切换到新路径，并删除旧路径

默认值建议：

- 正式文件默认 `switch`
- 草稿转正默认视为身份迁移，不保留草稿旧路径

## 5. 保存路径迁移与“另存为后删除当前路径”

### 5.1 语义拆分

这一轮要把“另存为”拆成明确的用户语义，而不是只有一个保存对话框：

#### 保存

- 写回当前路径

#### 另存为

- 选择一个新路径保存
- 当前会话切换到新路径
- 旧路径是否保留，取决于策略

### 5.2 新增行为：另存为后删除当前路径

当用户选择或设置为 `move` 时：

1. 先确保新路径写入成功
2. 再删除旧路径
3. 如果删除失败，必须保留新路径，并明确回退为“已另存，但旧路径未删除”

### 5.3 删除策略

考虑到删除是高风险动作，产品行为上仍要谨慎：

- 对仓库代码执行删除需要显式来自用户配置或当次操作确认
- 删除失败不能影响新文件落盘
- 对草稿旧路径，仍可沿用现有“身份迁移后移除旧草稿”的思路

### 5.4 UI 建议

在“另存为”入口附近增加一个可发现但不抢戏的选择：

- `另存为`
- `另存并迁移（删除旧文件）`

同时在设置里允许把默认行为改成其中一种。

## 6. 复制链路修复设计

### 6.1 问题判断

当前复制链路叠加了 Milkdown/ProseMirror 自己的结构序列化和自定义 `enhanceClipboard()` 的 HTML 改写，容易把块级边界和换行语义弄乱，表现为：

- 复制两段内容时多出一个空行
- 开头或结尾出现 `br`
- 同一份选择内容在不同目标应用里表现不一致

### 6.2 目标行为

复制出去的内容应满足：

1. 视觉上保留正常段落结构
2. 不额外引入人为的空白段落
3. 不泄漏孤立的 `br`
4. 保持富文本样式增强能力，但不能破坏内容语义

### 6.3 修复策略

先补最小复现测试，再动实现。实现上优先考虑：

- 只对允许增强的标签添加样式
- 不手写或保留多余 `br`
- 对复制片段的首尾空块做清理
- 明确区分“段落间距”和“文本换行”

---

## 7. 实施顺序

本轮实施顺序固定为：

1. **实时热更新修复**
   先把外部 Agent 修改当前文件后不刷新的问题彻底修掉
2. **标题/文件名同步**
   处理窗口标题、提示策略、双击改标题与路径重命名
3. **设置面板 + 路径迁移语义**
   加入悬浮设置面板，以及“另存为 / 另存并迁移”的明确入口
4. **复制链路修复**
   最后清理 clipboard 输出，补回归测试

这个顺序的理由是：

- 先修底座承诺
- 再修文档身份
- 再补承载这些策略的 UI
- 最后收剪复制体验

---

## 8. 验收标准

### 8.1 实时热更新

- 外部 Agent 以原地写入方式修改当前文件，LyraMD 自动刷新
- 外部 Agent 以 rename 覆盖方式修改当前文件，LyraMD 仍能自动刷新
- 同一文件连续多次外部修改后，无需重启应用

### 8.2 标题与路径

- 编辑文档首个标题后，窗口标题实时变化
- 标题与文件名不一致时，可触发一次受控提示
- 同步文件名后，当前会话、recent、workdir 状态一致

### 8.3 设置

- 设置面板可悬浮打开和关闭
- 可以修改标题同步策略
- 可以修改另存为默认行为

### 8.4 另存为迁移

- “另存为”成功后可切到新路径
- “另存并迁移”成功后可删除旧路径
- 若删除旧路径失败，不影响新路径保存成功

### 8.5 复制

- 复制两段普通段落时，中间不出现额外空行
- 粘贴结果开头和结尾不出现裸 `br`
